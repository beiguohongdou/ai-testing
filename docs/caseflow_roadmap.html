工作流程 · 公开分享版

caseflow · AI 赋能测试框架

把零散文档与抓包，变成有断言、防假绿、可复跑的接口与 UI 自动化资产

阶段一 需求对齐与素材准备 先梳理、再拍板、防瞎编 · 极低 Token 消耗
01
项目地图与配置门禁 初始化 · 安全防呆

运行 caseflow init 生成标准化骨架，用 PROJECT_MAP.md 梳理业务模块与上下游数据依赖；账号密钥统一置入 .env 占位脱敏，默认拦截疑似生产域名的非 GET 请求。

↓ 单模块推进 · 新开干净会话防上下文漂移
02
提纲、盲区与选择题拍板 AI 拆解 · 人工 2 分钟拍板

严格按材料三态（双源 / 仅 PRD / 仅接口）禁止编造字段；先输出 10～20 行带 [AUTO] 标记的提纲，主动列出隐含盲区（Unknowns）与口径冲突选择题，人拍板后再落代码。

↓ 分工原则：UI 扛 20% 核心主干流，接口扛 80% 参数边界与多步流
阶段二 双轨自动化落地 确定性工具底座 + 原生可调试 pytest
03A 轨道 A · Playwright UI 自动化
  • 多角色登录隔离：caseflow auth 过验证码存 .auth/*.json，通过 page_as 隔离会话。
  • 瘦身 DOM + 检查点：caseflow dom -i 手动走完前置状态抓取 1～2.5k Token 骨架，顺手记下「检查点备忘」。
  • 反脆弱与造数：按真实 DOM 写 PO 与 Web-First 断言；前置造数优先调接口 client()。
03B 轨道 B · 接口自动化
  • 极简 YAML 数据驱动：单接口多参数走 data/*.yaml，支持 base_json + drop、动态占位符与 xfail 探活。
  • 多步流原生 Python：api_as 进程内复用登录 + gen.* 造数 + finally 清理，兼容 code: 0 信封。
  • 深度测试能力：支持 diff_response 差分比对、不变量性质测试与跨角色越权检查。
↓ 编码只是开始 · 硬门禁与证据验证后才纳入回归
阶段三 硬门禁验证、排查与交付 要证据，不要声明 · 严防 AI 偷改预期凑绿灯
04
防改断言硬门禁 caseflow guard

自动扫描 git diff 中对 tests/ 与 data/ 的修改，强力拦截擅自删减 assert/expect、改弱 YAML 预期或私加 skip/xfail 的作弊行为，人工确认后方可 --allow 放行。

↓
05
防假绿变异与独立复核 caseflow mutate

故意清空响应体或翻转状态码/业务码，揪出「只检查 HTTP 200」的假绿用例（支持 --changed 增量与 --observe 观察模式），并建议用干净会话独立复核 diff 与报告。

↓
06
证据排查与反向出表 plugin · caseflow export

UI 失败自动留存全屏截图 + 去重控制台报错 + HTTP ≥ 400 请求到 reports/ui/；接口失败自动生成脱敏 curl 复现命令；caseflow export 1 秒导出最新 Excel/Markdown 用例表。

✓ 通过 · 沉淀回归资产

pytest、guard 与 mutate 全部通过，更新 PROJECT_MAP.md 并导出最新用例表，纳入长期回归。

! 失败或未执行 · 先查根因

先跑 pytest -m smoke 排环境，再看本机诊断包区分环境 / 数据 / 真 Bug（标 xfail_strict）或脚本问题。

↻
核心铁律：只有确认是脚本问题才改代码；严禁删减断言凑绿灯；涉及下单/扣款等写入类用例禁止盲目自动重跑（--reruns），写入结果不明时停机核查。
