# AI 测试工作流（caseflow v3 个人提效版）

> **核心定位**：AI 干 90% 的拆解、造数、编码粗活，人只在关键节点花 2 分钟拍板，再用**真实环境实测**校准文档盲区。  
> 工具包 `caseflow` 通过 `pip install` 全局或虚拟环境安装，不向业务项目复制框架源码。

---

## 前置：安全与脱敏红线

在把公司材料交给公网大模型之前，先做 3 件事：
1. **禁贴清单**：真实生产库连接串、真实 API Key / Token、个人隐私（身份证/真实手机号）、生产环境真实地址。
2. **账号密钥占位**：测试账号密码绝不写进代码或 YAML，统一放项目 `.env`，YAML 和配置里只写 `${ENV_NAME}`。
3. **防误打生产**：`caseflow.yaml` 默认拦截域名含 `prod / production / live / online` 的非 GET 请求。

---

## 三道强制停机门禁（必须严格遵守）

1. **配置门禁**：动笔写第一条用例前，先核对 `caseflow.yaml` 是否已脱离脚手架默认值（`envelope`、`login`、`roles`）且 `.env` 已建好；未就绪时**先只改配置并列出 `.env` 变量清单停下**，禁止直接冲去写用例。
2. **单模块门禁**：即使只收到“继续”，每轮最多只落地 **1 个模块**；写完必须在本轮跑通**全量 `pytest`**（防文件重名或破坏已有模块）和 **`caseflow mutate`**（接口模块防漏弱断言），更新 `PROJECT_MAP.md` 后停下来汇报。
3. **DOM 先行门禁**：写 UI 用例前，若没有目标页的真实元素依据（`reports/dom/*.md`、`codegen` 输出或本轮实测 DOM），先停下来给出 `caseflow dom <url> -i` 命令让用户抓取，禁止凭空猜定位器。

---

## Step 0 · 项目地图与模块上下游梳理（接手新项目/大文档第一步）

拿到大需求或跨多个页面/接口的项目时，**禁止一上来直接写测试代码**，先生成/更新项目根 `PROJECT_MAP.md`：

1. **业务模块划分**：把需求拆成独立模块（例如 `登录鉴权`、`商品浏览`、`购物车`、`结算下单`），标出每个模块对应的页面 URL、接口前缀和优先级（P0/P1/P2）。
2. **模块上下游依赖矩阵**（解决「先登录再加购再结算」断链问题）：
   | 下游模块 | 依赖上游 | 需要的状态 / 数据契约 | 推荐衔接方式 |
   |---|---|---|---|
   | 填写下游模块 | 依赖哪个上游模块 | 需要的 Token / 资源 ID / 前置业务状态 | UI 登录态 `.auth/` / 接口造数 fixture / `inject_storage` |
3. **公共前置 Fixture 清单**：梳理 `conftest.py` 已提供的共享 fixture（如 `api_as`、`logged_in_page`、接口造数 fixture），每做完一个模块就更新 `PROJECT_MAP.md`。
4. **防上下文漂移**：以后每次做新模块，**新开一个干净会话**，只 `@ PROJECT_MAP.md` + 当前模块需求/DOM，不把几十轮历史对话拖进新任务。

## Step 1 · 任意输入适配（材料三态）

先在输出首行声明当前材料形态：

| 手上材料 | 怎么处理 | 禁止行为 |
|---|---|---|
| **双源齐全**（PRD + 接口文档/抓包） | 先用一句话对齐业务规则与接口落点，标出不一致处 | 禁止跳过不一致点强行瞎写 |
| **仅 PRD**（无接口文档） | 先出**业务测试点清单**；UI 可先做主干草稿，接口列出需要找开发要的 `curl` / 文档清单 | **严禁**凭空编造 URL 路径、字段名、错误码 |
| **仅接口文档 / 抓包 curl** | 直接出**协议层 + 参数校验层**高确定性用例（必填/类型/边界/401）；缺失的业务流规则向人提问 | **严禁**把没写明的业务规则当成确定预期 |

> 非标文档（飞书表格、Word 截图、聊天记录里的 `curl`）一律照接，不要求必须是标准 OpenAPI JSON。

## Step 2 · 提纲与选择题拍板（唯一强人工卡点）

**不要让 AI 一口气直接吐 50 条长用例或直接写代码！** 按下面两步走，把用例准确率拉到 90%+，切断向自动化代码传递误差：

1. **先出 10～20 行精简测试点提纲**（人 1 分钟扫完）：
   - 列：`编号 | 模块 | 测试场景 | 预期方向 | [AUTO-UI / AUTO-API / 手工]`
   - 默认只有高价值 P0/P1 场景打 `[AUTO-*]`，低价值凑数用例标 `[手工]`，不进自动化。
2. **顶部集中提选择题**（遇到文档漏写、口径冲突，禁止瞎猜）：
   ```text
   【需你拍板】
   Q1：加购超过库存时，接口是直接拒绝还是下单时再校验？ A.加购直接拒绝  B.下单时校验  C.先标 xfail 实测看返回
   Q2：这批里面标 [AUTO] 的范围是否认可？
   ```
3. **人拍板后再落地**：用户回复 `1A 2确认` 后，再进入 Step 3 写用例与自动化代码（如果用户需要交付完整用例表，同时补齐或后续用 `caseflow export` 一键导出）。

## Step 3 · 双轨自动化落地

### 轨道 A：Playwright UI 自动化（主干流优先）

> **分工原则**：UI 只扛 20% 核心主干路与页面渲染/交互；80% 的参数边界、多组合异常交给接口轨道。

#### 1. 先打通登录与上游数据依赖
- **多角色登录隔离**：`caseflow auth <登录URL> --name <角色>`（默认 `user`）把登录态存为 `.auth/<角色>.json`。新脚手架默认让 `page` 保持干净未登录态，需要免登录的业务用例使用 `page_as("user")` / `page_as("admin")`，与登录/退出用例互不污染。
- **跨模块上游业务数据**：前置造数（如注册一次性临时账号）和清脏数据（清空购物车/收藏）**优先直接调用接口 `client()`**，不要在 UI 里用 `if locator.count():` 碰运气清理（存在异步加载竞态，又慢又不稳）。

#### 2. 获取页面元素的两种方式与成本选型
| 方式 | 怎么操作 | Token 消耗 | 推荐模型 | 适用场景 |
|---|---|---|---|---|
| **方案 1：脚本抓瘦身 DOM（主力，最省钱稳定）** | 单页直接 `caseflow dom <url> -o page.md`；**需先走完上游操作/弹窗的**用 `caseflow dom <login_url> -i`（浏览器里手动点到目标状态再回车抓取），或用 `playwright codegen` 录一段草稿 | **极低**（每页 50～150 行交互骨架，约 **1,000～2,500 Token**） | 任意主流代码/对话模型（如 DeepSeek、Qwen、Claude Sonnet/Opus、GPT 等）均可高准确率完成 | 日常 90% 的页面元素获取与 PO 编写 |
| **方案 2：Browser MCP / Agent 自主点击探索** | 让带浏览器工具的 Agent 自己点开页面、读 Accessibility Snapshot 或截图 | **偏高**（多轮截图 + 树回传，单页流程常 **1.5万～5万+ Token**） | 必须使用强 Tool-Calling / 多模态模型（如 Claude 3.5+/4/Opus、Gemini 2.5+/Pro、GPT-4o+） | 无人值守探索陌生系统，且预算充足时 |

#### 3. 生成 PO 与原生 Playwright 用例的铁律
- **先做映射表，再写代码**：拿到瘦身 DOM 后，先对照测试步骤确认「每一步操作/断言对应 DOM 里的哪个 `data-testid` / `role` / `label`」，找不到就直接提示「页面缺该元素（可能缺上游状态）」，**严禁凭想象编造定位器**。
- **定位器优先级**：`get_by_test_id` > `get_by_role(..., name=...)` > `get_by_label` > `get_by_placeholder` > 稳定 `id`/`name`；避开动态长数字 id、`.nth()` 和样式类名。
- **反脆弱铁律**：
  - **严禁 `time.sleep()`**。
  - **异步回填表单防覆盖**：遇到进入页面后会自动拉取默认值回填的表单（如结算页默认地址），必须先等回填接口响应完成（`page.expect_response(...)`）或默认值出现后再 `fill()`，避免刚填完被晚到的回填覆盖清空。
  - **必须用 Web-First 断言**：`expect(locator).to_be_visible()` / `to_have_text()` / `to_have_count()`，禁止用 `assert locator.inner_text() == ...`（不会自动等待，极易偶发挂）。
  - 用例 docstring 第一行写 `TC-编号 标题`（供 `caseflow export` 扫描出表）。

### 轨道 B：接口自动化（数据与逻辑分离）

#### 1. 选对形态（YAML 红线）
- **单接口多组场景（正例 / 边界 / 异常参数）→ 走 `data/*.yaml`**：
  - 条件：单接口 + 无分支逻辑 + 单条数据清晰简洁。支持顶层 `base_json` + 用例 `drop: [字段]` 测必填缺失，避免重复抄写大段字段。
  - 在 `tests/api/test_xxx.py` 只写 `@pytest.mark.parametrize("case", load_cases("data/xxx.yaml"))` + `run_case(case)`；改完 YAML 直接 `pytest`，**无需编译生成步骤**。
  - YAML 动态占位符：`${unique}`、`${phone}`、`${timestamp}` / `${timestamp:ms}`、`${today:-1d}`、`${now}`、`${len:255}`、`${alpha:8}`、`${digits:6}`，同条用例复用写进 `vars`。
- **多步业务流（建单→支付→查单→清理）/ 需要条件分支或加解密 → 直接写原生 Python**：
  - 使用 `api = client("user")`（进程内按角色自动复用登录，不触发限流）。
  - Python 代码直接 `from caseflow import gen` 调用 `gen.unique()`、`gen.today("-18y+1d")`、`gen.phone()`、`gen.text(251)`，不必绕弯调用 `fill("${unique}", {})`。
  - 链式断言：`resp.expect_ok().expect("data.id", exists=True)` 或 `resp.expect_code(10001)`（兼容国内 HTTP 200 + `body.code` 信封）。
  - 测试造出的资源放在 `try ... finally` 里调删除接口清理；清理失败可忽略或打警告，不掩盖主流程失败。

#### 2. 文档漏写错误码 / 已知缺陷 → `xfail` 与 `xfail_strict`
- 遇到文档漏写错误码、待实测校准的用例：YAML 写 `xfail: 待实测校准`（`strict=False`）先打一枪测试环境，核对后再固化预期。
- 确认是**被测系统真缺陷**：YAML 写 `xfail_strict: 缺陷说明`（或 Python 加 `@pytest.mark.xfail(strict=True, reason=...)`），缺陷修复后自动变 XPASS 提醒移除标记。

## Step 4 · 排错防作弊、防假绿与反向出表

### 1. 排错 4 条规矩
1. **先排环境**：大面积超时或 `ConnectionRefused / 502 / 503` → 先跑 `pytest -m smoke`，冒烟不过立刻停止，不乱改用例代码。
2. **禁止偷偷改预期作弊（红线）**：AI 修复报错时，**严禁为了测试变绿擅自放宽或删掉 `expect` / `assert` 断言**！实际输出与预期不一致时，只准列出来让用户判定：
   - 需求口径变了 → 经用户同意后更新用例预期；
   - 被测系统真 Bug → 标 `@pytest.mark.xfail(strict=True, reason="缺陷号/现象")` 留痕，直接把报错附带的 `[复现] curl` 或 `reports/ui/*.md` 诊断文件丢给开发。
3. **小步最小修改**：只改报错相关的函数/数据行，改完立刻重跑该文件验证。
4. **UI 失败先看诊断包**：`caseflow.plugin` 已自动把失败截图、控制台报错和 HTTP ≥ 400 接口请求写到 `reports/ui/`，先看接口再看控制台最后查定位器。

### 2. 防假绿与用例导出
- **防假绿检查**：接口用例写完后运行 `caseflow mutate tests/api`，把响应故意改空或翻转状态码/业务码，揪出「只检查 HTTP 200」的假绿用例。
- **随时出表交差**：运行 `caseflow export`，自动扫描真正在跑的 `data/*.yaml` 和 `tests/**/test_*.py`，在 `reports/` 生成最新 `用例表.csv`（Excel 直接打开）和 `用例表.md`。
