# AI 测试工作流

本技能**自包含**，不依赖特定仓库路径。公司目录约定以用户当前项目为准。

原则与检查清单速查（可选）：本技能目录下的 `reference/知识框架速查.md`（`install.ps1` 一起安装）。

## 前置：粘贴材料前（所有工作流通用）

用户 `@` 或粘贴 PRD、接口文档、日志、traceback 时，**先执行**：

1. **能不能贴** — 整份生产契约、完整生产日志 → 要求节选或拒绝直贴
2. **节选** — 只保留与当前任务相关的段落
3. **脱敏** — 按占位符替换：`<TOKEN>` `<HOST>` `<USER>` `<PHONE>` `<ORDER_ID>` 等；自己动手，不交给 AI 事后删
4. **再进入** WF-1～9

排错改代码时：脱敏后走 WF-4，改动范围遵循**最小改动**（只改报错相关行，先方案后人审）。

## 任务路由

| 你在干什么 | 工作流 |
|------------|--------|
| 写/改提示词 | WF-1 |
| 接口/需求 → 用例 | WF-2 |
| 生成测试数据 | WF-3 |
| pytest 报错 | WF-4 |
| 审查 AI 写的 pytest | WF-5 |
| Swagger/OpenAPI → pytest 代码 | WF-6 |
| 审查/补全断言（防假绿） | WF-7 |
| 用例不可重复 / 数据残留 | WF-8 |
| UI截图→PO / 定位器自愈 | WF-9 |

## WF-1：四段式提示词 + 评审清单

**触发**：用户要写/改提示词，或要求按框架写 prompt。

### 步骤

1. 用四段式起草：

```text
你是 [角色]。基于以下 [材料]，完成 [任务]。
约束：
1）[约束1]
2）[约束2]
输出格式：[格式要求]
```

2. 约束须包含：仅依据提供的材料；不确定标「待确认」；不编造字段/状态码
3. 交付提示词后，附**评审清单**自评（完整性 / 可执行性 / 范围一致性 / 安全性）
4. 输出评审结论：

```text
## 评审结论
通过：X 条 / 需修改：X 条 / 建议补充：X 条
```

## WF-2：材料三态 → 矩阵 → 用例表 → 二道闸 → 人工确认

**触发**：用户要根据接口文档、OpenAPI、API 说明、PRD 生成测试用例。

### 输入

用户 `@` 提供的材料。无材料则要求提供，不凭空生成。

### 步骤

**⓪ 材料三态判定**（必做，先于一切）

| 手上有什么 | 走哪条线 | 禁止 |
|------------|----------|------|
| 仅 PRD | 出「验收点清单」（轻模板，见下） | 填 HTTP 码、字段名、required/enum |
| 仅契约 | 出协议层用例表 + 「待产品确认范围」 | 把 PRD 未验收的接口写成必测 |
| PRD + 契约 | ① 矩阵 → ② 用例表 | 跳过矩阵直接写表 |

判定结果写在输出第一行：`材料形态：仅 PRD / 仅契约 / 双源`。

**⓪+ 风险分级**（紧跟三态判定）

| 对象（接口 / 验收点） | 风险 | 理由 |
|------------------------|------|------|

- 高：涉及资金、权限 / 越权、不可逆的数据写入、对外暴露，或近期有变更、出过线上缺陷
- 中：普通数据写入、核心查询；低：只读、展示类
- 覆盖目标按风险定：高 = 1 正 3 反 + 边界；中 = 1 正 1 反；低 = 仅正例
- 风险理由写不出依据时标「待确认」，按中处理
- 第二行写 `非功能范围：性能 / 安全 / 兼容 —— 本轮不测 / 由 <负责人> 负责`，不默认包含

**① 双源对齐矩阵**（仅双源时；单源跳到 ②）

| 行ID | PRD验收一句 | 契约落点(method+path) | 规划case_id | 断言来源 | gap |
|------|-------------|------------------------|-------------|----------|-----|

三种 gap 必查：PRD 有契约无 → 待契约补全；契约有 PRD 无 → 待产品确认范围；语义冲突 → 标 gap 等澄清。gap **不写进用例预期**。

**② 生成用例表**

双源 / 仅契约 用固定 7 列：

| case_id | matrix_row | title | steps | expected | assertion_source | pending |
|---------|------------|-------|-------|----------|------------------|---------|

- `assertion_source`：契约 / PRD / 开发
- 双源时 `matrix_row` 必填，须回指 ① 的某一行
- 材料未写明的预期 → `pending` 列标「待确认」

仅 PRD 用轻模板，**不套 7 列**：

| 验收点 | PRD 原文（节选） | 缺什么（待接口文档 / 待产品） | 建议问产品/开发的问题 |
|--------|------------------|-------------------------------|-----------------------|

**③ 闸 1：材料核对**

| 检查项 | 查什么 |
|--------|--------|
| 状态码 | HTTP 码是否在材料 responses 里 |
| 字段名 | 请求/响应字段是否与材料一致 |
| 必填与 enum | 是否臆造 required 或枚举外取值 |
| 未文档化行为 | 是否把材料没写的业务写成必过预期 |

**④ 闸 2：文档交叉**

| 检查项 | 查什么 |
|--------|--------|
| 材料依据 | 每条预期能否指向材料某句 |
| 范围一致 | 是否超出已确认范围 |
| 待确认 | 「待定」是否被写死为确定结论 |
| 敏感信息 | 是否出现真实密钥、生产标识 |

**闸的出处要求**：③④ 每个检查项后必须写材料定位（如 `见 PRD §3.2` / `见 OpenAPI POST /orders → responses.400`）。**写不出出处 = 该项不通过。**

**缺条 ≠ 失败，编条 = 闸不过**：覆盖目标（按 ⓪+ 风险分级）达不到 → `pending` 写「契约未定义 / PRD 未覆盖」，算通过；为凑数写出材料里没有的触发条件/状态码 → 闸 1 不通过。

**⑤ 输出**

1. 首行 `材料形态：…`，第二行 `非功能范围：…`
2. 风险分级表；矩阵（双源）或缺口清单（单源）
3. 用例表 / 验收点清单
4. `## 二道闸结论`：通过 / 不通过 + 不通过项清单，**每项带出处**
5. `## 待你确认`：gap 处理建议 + pending 中哪些可放行、哪些阻塞
6. 不通过 → 修正后重跑（最多 2 轮）

**⑥ 人工确认点**：用户对「待你确认」表态前，**不进入 WF-3 / WF-6**。

**⑦ 待确认落盘**：`## 待你确认` 的每一条同时追加到项目 `docs/待确认.md`（没有就建），只在对话里出现不算记录：

| 编号 | 类型 | 问题 | 问谁 | 提出日期 | 答复 | 答复日期 | 回写位置 |
|------|------|------|------|----------|------|----------|----------|

- 编号：双源用矩阵行ID，YAML 模式用 case_id；类型：gap / pending
- 答复后先回写矩阵 / 用例表（YAML 模式改 `cases/*.yaml` 并删掉对应 pending），再补全本行；**不删行**，留作 pending 关闭时长的统计来源

### 成功标准

材料已脱敏节选；所有 gap / 未定义项落在矩阵或 `pending`，无一写成必过预期；闸每项有出处。**条数不是标准。**

### YAML 模式（项目根有 `aigen.yaml` 时走这条）

用例不写 Markdown 表，直接写成 YAML 用例（IR），YAML 是唯一数据源；用例文档由程序导出。

1. 先读 `aigen.yaml`（材料、账号常量、身份、页面对象目录）和 `aigen/draft_rules.md`（起草规则，**全文**）
2. 双源时仍先出 ① 矩阵；再按规则写 `cases/<module>.yaml`
3. 运行 `python -m aigen validate`：出处会到契约 / PRD 原文核对；不过就改，最多 3 轮
4. `## 待你确认`：按 validate 汇总的 `pending` 类型列出，并按 ⑦ 落盘；**用户表态前不 render**
5. 用户确认后：`python -m aigen render` → `trace` → 运行 pytest（失败走 WF-4）→ `mutate`（报 `[WEAK]` 走 WF-7）→ `export`（用例表.md / .csv / 验收覆盖.md）
6. CI 门禁：`python -m aigen check`（validate + trace + selftest + 运行接口用例 + mutate，任一失败或 `[WEAK]` 即不过）；UI 用例另跑 `pytest testcase/ui_gen`

批量起草（无人值守 / CI）：`python -m aigen draft <module> [--ac AC-01,AC-02]`，模型配置在项目根 `.env`（见 `aigen/.env.example`），产出同样要人工评审。
项目还没有 aigen：`install.ps1 -ProjectRoot <项目> -WithAigen`，再把 `aigen/aigen.yaml.example` 复制成项目根 `aigen.yaml` 修改。

## WF-3：等价类 → 结构化数据 → 校验重试

**触发**：用户要生成测试数据、边界数据、YAML/JSON 测试数据。

### 步骤

**① 等价类脑暴**（每字段至少三类：正常值 / 边界值 / 异常值）

**② 结构化输出** — JSON/YAML；多字段用风险优先抽样

**③ 校验** — 类型、必填、枚举、字段名与材料一致

**④ 校验失败重试**（用户反馈错误时）：

```text
你是测开。下列数据未通过校验，错误如下：
{字段路径与原因，已脱敏}
请只输出修正后的数据，字段集合与业务含义不变，不要新增文档未出现的业务字段。
输出格式：与第一次要求一致。
```

## WF-4：traceback → 分类 → 最小修改 → fix loop

**触发**：用户贴 pytest/traceback 报错，或要求按框架修复失败用例。

### 步骤

1. **无 traceback → 要求提供**，不猜测修改
2. **先排除环境**：大面积同时失败，或异常是连接类（ConnectionError、Timeout、集中 502/503）→ 先跑冒烟（`pytest -m smoke`；没有 smoke 就发一条登录或健康检查请求）。冒烟不过 → 归类「环境」，**终止，不进 fix loop、不计轮次、不改任何用例**，报环境负责人
3. 读三要素：异常类型 / 异常描述 / 文件与行号
4. `FixtureError at setup` → 改 fixture，不改用例逻辑
5. 分类：断言失败 / fixture 链 / 环境或数据 / 产品缺陷 / **需求不明确**
6. **需求不明确**（PRD 未定义、多口径冲突）→ **立即停止**，标「待产品确认」，不猜测修复
7. **产品缺陷** → 不改用例；人确认是缺陷后输出「缺陷提单草稿」（见下方模板），人提交后把单号回填到 `known_issue: 单号`（YAML 模式）或 `xfail(strict=True, reason="<单号>：…")`；缺陷修好出现 XPASS → 删标记并按回归规则复测
8. 给方案：只改报错相关行；1～2 个假设 + 验证方式；先脱敏；**禁止**为通过测试直接改断言预期
9. **fix loop**：人审后执行 → 复测；仍失败且未达轮次上限（默认 **3 轮**）→ 下一轮；达上限 → 停止，写升级说明
10. 修复依据顺序：定稿 PRD/用例表/接口文档 → 业务逻辑 → traceback → 测试代码
11. 终止后产出 **一页小结**（见下方模板）

### 缺陷提单草稿模板

```text
## 缺陷提单草稿
- 标题：[模块] 现象一句话
- 关联用例：case_id 或 测试文件::函数名
- 严重度：致命 / 严重 / 一般 / 轻微（依据：影响范围、有无绕过方式）
- 环境：<HOST> / 版本 / 时间
- 复现步骤：1. 2. 3.（数据已脱敏）
- 预期：…（出处：见 OpenAPI … / 见 PRD §…）
- 实际：状态码 + body 节选（已脱敏）
```

### 回归范围规则

mark 约定（在项目 `pytest.ini` 的 `markers` 注册）：`smoke` = 登录 + 每个模块 1 条主路径，几分钟内跑完；`core` = 高风险用例（WF-2 ⓪+ 风险为高）；全量 = 不带 `-m`。

| 改了什么 | 至少回归 |
|----------|----------|
| 单条用例 / 断言 | 本文件 |
| fixture / conftest / 公共数据 / 工具函数 | 所有用到它的用例（`pytest --fixtures-per-test` 或 grep 查引用）+ `smoke` |
| 被测系统发版 / 缺陷修复（XPASS） | `core`；发版前跑全量 |

YAML 模式生成代码不加 mark，回归直接跑 `python -m aigen check`。

### 一页小结模板（Markdown）

```text
## 执行概览
- 时间 / 范围 / 通过数 / 失败数 / 耗时 / 退出码

## 失败与修复
| 用例 | 根因类别 | 修改点 | 人改/机改 | 轮次(x/3) | 缺陷单号 | 结论 |

## 回归范围
- 按「回归范围规则」选的层级 + 实际执行的目录 / mark

## 残余风险
- （诚实写，勿编造「已彻底解决」）

## 升级人工（如有）
- 达轮次上限或需求不明时的说明与思路
```

## WF-6：Swagger → pytest 骨架 → 评审 → 补全

**触发**：用户要从 Swagger/OpenAPI 生成 **Python + Requests + pytest** 接口自动化代码。

**与 WF-2 区分**：WF-2 产出 **Markdown 用例表**；WF-6 产出**可执行代码**。先表后码。

**项目根有 `aigen.yaml` 时**：不走下面的阶段 A～C，代码由 `python -m aigen render` 从 YAML 用例按模板生成（不经过 AI），见 WF-2「YAML 模式」。生成文件**禁止手改**（`trace` 会报）；要改就改 YAML 再 render。人只评审 YAML，不评审生成代码。

### 输入

- Swagger/OpenAPI 或接口说明（`@` 引用，先脱敏）
- **业务说明**（必填项）：鉴权规则、数据溯源（token 从 login、user_id 从 user info 等）
- 可选：现有 `tests/` / `conftest.py` 结构（AI 须适配，不得臆造框架）

### 阶段 A：仅 skeleton + TODO

1. 先抽 **1～2 个**接口（或用户指定 login 链）
2. 生成：
   - `conftest.py` fixture **骨架**（如 session 级 client）
   - 测试文件：`requests` 调用 + **`# TODO:` 单行** + 上方多行注释（任务、数据来源）
3. **禁止**阶段 A 写满：完整 assert、重试库、熔断、复杂日志
4. 输出时标注：`## 阶段 A：骨架（待人工评审）`

### 人工评审闸（必须）

评审清单：

| 检查项 | 查什么 |
|--------|--------|
| TODO 顺序 | 是否符合业务流 |
| 数据溯源 | token/user_id 来源是否写清 |
| 冗余 | 重复 existence 断言等 |
| 过度实现 | 是否偷偷写满代码 |
| 安全 | 无明文 token/密码硬编码 |

**未通过 → 只改骨架，不进入阶段 B**

### 阶段 B：补全代码

用户确认「评审通过」后：

1. 补全 TODO 为真实断言与提取逻辑
2. **优先断言响应 body**；401 等错误码结合 body；主路径通过后再补反向用例
3. token/secret 从环境变量读；提醒提供 `.env.example`
4. 符合项目现有 fixture 约定（见 WF-5）

### 阶段 C：组织与执行

1. 建议按**业务流**分子目录或 class
2. 运行 `pytest`（先冒烟，见 WF-4 第 2 步）；失败 → **WF-4** fix loop
3. 不擅自修改用户提供的业务说明、TODO 意图、契约字段

### 输出

1. 骨架或完整代码（视阶段）
2. `## 评审结论` 或 `## 阶段说明`
3. 鉴权溯源说明（token / user_id 链路）

## WF-7：断言审查与补全（body + status）

**触发**：审查或补全 pytest/Requests 断言；用户担心假绿；反向用例设计。

### 步骤

**① 断言顺序检查**

- [ ] 主路径：**先 body 关键字段**，再 status
- [ ] 反例：**先 body 错误要点**，再 status（均在契约 responses 内）
- [ ] 无 body 接口 → 须**说明原因**（代码注释或简报）

**② 假绿风险扫描**

| 风险 | 处置 |
|------|------|
| 仅 assert status | 补 body 断言或标注假绿风险 |
| 删掉 body 断言仍绿 | 必须修复 |
| AI 生成缺 body 检查 | 人工补全，不依赖 AI 自查 |

**③ 反向用例**（至少审视 1 组）

- 固定触发 + 契约内 status + 可复现数据
- 禁止 flaky、「非 2xx 即可」

**④ 执行结果分类**（实际跑过后）

对照契约，归入四结果之一并写 reason：

| 结果 | 何时 |
|------|------|
| 红→绿 | 可修 |
| 维持红 | 需求不明，或疑似缺陷但尚未人工确认 |
| xfail | 实返超出契约定义的状态码（契约滞后，reason 写「待确认」） |
| xfail(strict=True) | 人工确认的产品缺陷（如应401却500）；reason 必须带缺陷单号；修好后 XPASS 提示删标记 |

**skip 不用于产品缺陷**：只用于环境或前置条件不具备（缺账号、依赖服务未部署），reason 写明缺什么。skip 修好不会报警，缺陷会变成盲区。YAML 模式下缺陷一律写 `known_issue: 单号`。

**⑤ 输出**

```text
## 断言审查报告
### body+status 合规项 / 假绿风险项
### 反向用例稳定性
### 修复四结果建议（含 xfail/skip reason 草稿）
```

**Check 前**：重新读取目标测试文件内容，不用旧缓存。

## WF-8：可重复性诊断与清理策略

**触发**：用例「第一次绿、第二次红」；连跑不稳定；设计 register/下单等多步 flow。

### 步骤

**① 诊断**

- 连跑 2～3 次同一用例/同一文件
- 判断残留类型：创建型 / 状态变更型 / 只读（只读无需清理）
- 判断接口是否幂等（设计属性，人确认）

**② 推荐策略**（按优先级）

```
幂等覆盖 → delete/回滚（best-effort） → skip-on-exists + README
```

| 策略 | 适用 |
|------|------|
| 数据轮换 | 单接口调试；finalizer 改 YAML username |
| delete 接口 | teardown/finalizer 调业务删除；**禁止**直操库 |
| skip-on-exists | 无 delete；400 已存在 → pytest.skip |

**③ 实现要点**

- 清理失败：`logging.warning`，**不 raise**（清理失败 ≠ 用例失败）
- 多资源清理：优先 `addfinalizer`；`addfinalizer(fn)` 非 `fn()`
- 状态变更 flow：README/agents.md 写「不断言余额绝对值」等

**④ 输出**

```text
## 可重复性诊断
### 残留类型与根因
### 推荐策略（含代码/finalizer 草稿）
### README/agents.md 须补充的说明
```

## 线上缺陷回流

线上缺陷（含复盘）一律补回归用例，否则同类问题会再次逃逸：

1. 材料 = 缺陷单节选（先脱敏），不需要 PRD
2. 至少 1 条能复现该缺陷的用例；`req_ref` 写缺陷单号（如 `BUG-123`），出处写 `实测 日期`
3. 风险分级直接标「高」（WF-2 ⓪+），进 `core`
4. 修复前用例按 WF-7 标 `known_issue` / strict xfail，修复后 XPASS 删标记

## 度量（每个迭代记一次）

追加到项目 `docs/度量.md`，一行一个迭代，只记这三项：

| 指标 | 取数来源 |
|------|----------|
| pending 关闭时长（中位数）+ 未答复条数 | `docs/待确认.md` 的提出日期 / 答复日期 |
| fix loop 达上限比例 | 一页小结「轮次」列为 3/3 的条数 ÷ 失败总条数 |
| 弱断言占比 | `aigen mutate` 末行「存活 / 变异体」；非 aigen 项目用 WF-7 假绿风险项数 ÷ 审查用例数 |

趋势变差时先查流程，不先怪执行：pending 时长变长 → 查 WF-2 ⑦ 有没有落实「问谁」；达上限比例变高 → 查是否把环境问题带进了 fix loop（WF-4 第 2 步）。

## WF-9：截图驱动PO生成 + 定位器自愈

**触发**：用户给截图要生成 Page Object，或 UI 定位器失败要修复。

### PO 生成流程

1. 确认用户提供 agents.md（技术栈+工程结构）、截图（完整页面，下拉展开后截全）
2. 生成 Page Object，定位器：id > name > 稳定属性 > 相对 XPath，避开动态属性
3. 自检 PO 定位器可用 → 全绿后生成用例和数据 → To-do 追踪各阶段

### 定位器自愈

```
定位失败 → 采集 DOM / Page Source → 只贴出错元素附近的 HTML
  → 先判断：元素在 DOM 里还在、只是属性变了？
    → 否（元素消失 / 页面结构大改）→ 不自愈，直接判失败，按疑似 UI 回归走 WF-4
  → AI 给新定位器 → 复测
    → 成功 → 输出「旧定位器 / 新定位器 / 命中元素截图」→ 人确认是同一个元素 → 更新缓存
    → 失败且未达 3 轮 → 下一轮
    → 达上限 → 标记失败，记入失败缓存
```

自愈只修「同一个元素换了定位方式」。复测通过不等于找对了元素：AI 可能命中一个长得像的元素，把真实 UI 缺陷「自愈」成绿色，所以写缓存前必须人确认。

### 验证码

不强解。优先找开发要万能码 / 关闭验证码；其次手动登录拿 cookie；复杂验证码放弃，标注人工介入。
